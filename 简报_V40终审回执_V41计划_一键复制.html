四、【B4】延期计数按「次」累计：可实现，但要加一个字段

可实现，且能严格满足「同一天多次延期算多次、跨天累加不重置」。做法：
需求实现口径落点
计数按「次」累计，同一天多次延期算多次 用整数计数字段 defer_count INTEGER NOT NULL DEFAULT 0，每次延期 +1，永不按天重置。 「同一天多次延期算多次」= 一天内点 3 次延期就是 3，不是 1。天然满足。 reminders 表加一列；lib/data/reminder.dart 的 Reminder 模型加 deferCount 字段。
到期当天未处理 → 自动延期 → 到期当天再次提示 自动延期 = 把 due_at 往后推一天（不新建条目），条目仍在待办流里，所以「再次提示」= 同一条目重新出现在催办区。不产生重复行。 提醒读取时判定「due_at < 今天 且未完成 → 自动推一天 + defer_count + 1」。
「已延期 N 次」跨天累加不重置（按次累计，非按天） defer_count 只增不减，与日期无关——第 3 天显示「已延期 3 次」，不是「已延期 1 次」。天然满足。 同上字段。
【B3】每条可加文字备注（处理备注/延期原因），备注随条目保存，导出时一并带出 现有 reminders.detail 列已经是备注列，可复用（编辑弹窗里已有「备注」输入框）。但「处理备注」与「延期原因」语义不同，建议加一列 handle_note 专放处理备注/延期原因，避免与原始 detail 混淆。 reminders 表再加一列 handle_note。
连带影响：schema v11 → v12。两库同步升级（生活库迁移 + 工作库新建），八表口径不变（仍是 v11 的 8 张表 + reminders 表加 2 列）， 「工作库八表与 v11 逐表核对」那条验收观察项的口径要相应更新为 v12 逐表逐列核对——我会同步更新专项测试与台账，不让这条观察项悄悄失效。
迁移是纯增量（ALTER TABLE ADD COLUMN，已核对仓库里有 _addColumnIfMissing 的幂等加列工具，升级幂等不会重复加）。

五、docx 真机复验（【F③】【G#1】【J】）：程序化验证已做到极限，真机那一刀留给 PM

元宝的判定我完全接受：「ZIP 结构校验通过 ≠ Word 可打开可编辑」。所以我把程序化验证从「ZIP 结构」往上推了三层， 但仍不冒充真机结论。
层手段结果
① ZIP 完整性 zipfile.testzip() 全量 CRC 校验 PASS CRC 全通过
② OOXML 部件与 XML 良构 6 个部件齐全（[Content_Types].xml / _rels/.rels / word/document.xml / word/styles.xml / word/_rels/document.xml.rels / docProps/core.xml）；每个 .xml/.rels 用 ElementTree 解析 PASS 部件齐全、XML 全部良构
③ 真实文档引擎解析 macOS textutil（Apple 文档引擎，Pages/TextEdit/预览同款）读出全文 9 段，中文/「□」「·」「→」「—」全正常 PASS 能读能取文本
④ 往返转换 textutil -convert docx：我们的 docx → textutil 重新序列化 → 再读，文本一字不差；产物含 word/theme/theme1.xml 等 Apple 自己补的部件——说明引擎把它当正常 Word 文档处理并加工了 PASS 可读 → 可编辑 → 可再存
第 ③④ 层是关键证据：textutil 不是「只会解 ZIP」的检查器，它真的按 OOXML 语义建了文档模型并重新序列化， 还自动补上了 theme1.xml——这与 Word/WPS 打开是同一条技术路径。
但我仍然不宣称「真机通过」：textutil 是 Apple 引擎，不等于微软 Word 或金山 WPS，二者对 OOXML 的宽容度不同（尤其 WPS 对缺省部件更敏感）。 PM 用 Word/WPS 打开一次，这一条才算真的过。
