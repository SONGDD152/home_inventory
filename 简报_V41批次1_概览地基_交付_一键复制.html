一、★ 请元宝追认：对字段清单的唯一一处增补（next_due_at）

元宝裁定的 9 个字段我全部照办： id / source_type / source_id / status / done_at / defer_count / handle_note / created_at / updated_at——字段名、类型、默认值全部照原样，无改名、无改型。

我多加了第 10 列 next_due_at INTEGER（可空）。

为什么必须加这一列（不是可有可无的锦上添花）

元宝 B4 的原话是：「到期当天未处理 → 自动延期 → 到期当天再次提示 → 每次延期计数+1，显示「已延期 N 次」，计数跨天累加不重置（按「次」累计，非按天）」。

要让这条成立，必须存得下「下一次提示的时间点」。而 9 个字段里没有任何一个能装它：

候选方案后果判定
① 推 reminders.due_at（改日程表） 概览 / 日报页就越界写日程表了——破了 PM 拍板的「概览只写待办状态、不碰其他表」边界，也破了元宝自己批的「概览只读代码层落实」 否决
② 用 defer_count 反推天数（有效到期日 = 原到期 + N 天） 「按次累计」直接退化成「按天累计」。一条过期 5 天的提醒，一次打开就显示「已延期 5 次」，而用户实际只被提示过 1 次——与 B4「按次累计，非按天」直接冲突 否决
③ 单独存「下一次提示时间」 延期次数与提示次数解耦：手动延期一天点 3 次 = 3 次（按次）；自动延期每天最多 +1 次（防止过期 5 天一天涨 5 次，计数失真） 采用
所以 next_due_at 是延期机制的必要存储位，不是「新催办源」的表结构扩展—— 它不违反元宝「后续加新源只加枚举值、不加表不加列」那条约束（那条约束针对的是新增催办源，不是延期机制本身）。

若元宝仍要严格 9 列，退路是：把 next_due_at 砍掉，改用方案 ①（推 reminders.due_at）， 代价是概览越界写日程表，与刚拍板的边界冲突——我不建议，请元宝二选一。

实际建表 SQL（已落地）

CREATE TABLE IF NOT EXISTS todo_states (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  source_type   TEXT    NOT NULL,             -- schedule_reminder | loan_due
  source_id     INTEGER NOT NULL,             -- reminders.id | loans.id
  status        TEXT    NOT NULL DEFAULT 'pending',  -- pending | done | deferred
  done_at       INTEGER,
  defer_count   INTEGER NOT NULL DEFAULT 0,   -- 按「次」累计，跨天不重置
  handle_note   TEXT,                         -- 处理备注 / 延期原因
  next_due_at   INTEGER,                      -- ← 延期后的下一次提示时间（增补列）
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_todo_states_source
  ON todo_states(source_type, source_id);     -- 一个源条目只允许一条状态记录
CREATE INDEX IF NOT EXISTS idx_todo_states_status     ON todo_states(status);
CREATE INDEX IF NOT EXISTS idx_todo_states_next_due  ON todo_states(next_due_at);

三、E1 真 bug 的修复与实证

V4.0 的 E1 是覆盖 + 重复的双 bug：生活区与工作区的源共用 id='loan_due' 与 displayName='借出到期'，而概览拿 displayName 当 Map key → 工作区把生活区的借出到期条目整个覆盖吞掉，且标题还渲染两次。

本次修法两道，缺一不可（只改名是糊弄）：

  1. Map 的 key 从 displayName 换成 source.id——唯一标识做 key，展示名只管展示；
  2. 源的 id / displayName 本身带域——id='loan_due_life' / 'loan_due_work'。

还有一处元宝清单外但必须做的：条目 id 也要带域（loan_{域}_{id}）。

原因：条目 id 会当 widget key 用（overview_entry_{id}）。生活区和工作区各有自己的 loan_1 时，key 会撞——Flutter 里撞 key 会出断言错误或定位到多个 widget。 条目 id 带域后彻底隔离。状态配对另走 stateKey = '{source_type}_{source_id}'， 两套键各司其职：widget key 负责渲染唯一，业务键负责状态配对。
实证（专项测试锁死）：两域各有一笔借出时， lifeSource.id != workSource.id、displayName 各含「生活区」「工作区」、 两边的条目都能取到（V4.0 时生活区的会被吞掉）、条目 id 互不相同。

四、写边界：为什么「概览改不了账」在编译期成立

元宝 I③ 是这批改动的地基，所以单独说清楚：

接口能读能写入参
OverviewReader（一字未改） 物品 / 在库 / 在借 / 废弃 / 总拥有 / 守恒账平 无任何写方法 —
TodoStateWriter（新建） 待办条目状态 只写 todo_states 表 sourceType(String) + sourceId(int) + 枚举/布尔
关键：TodoStateWriter 的签名里没有任何仓储类型—— 没有 InventoryRepository、没有 InventoryDatabase、没有 ReminderRepository、 也没有 Item/Loan/Reminder。 概览页只持有这个接口，就编译期拿不到账的写能力——不是靠「UI 没放按钮」这种自觉。

三条回归锁（专项测试）： ① 源码级断言：待办写口签名不含任何仓储类型（将来谁塞一个进去，测试立刻红）； ② 源码级断言：概览页文件不含任何仓储类型； ③ 行为级断言：打勾后物品清单与在库数量一行不动，变的只有待办状态。
一处我自己踩到并纠正的坑：我第一版写的只读边界断言是 expect(writer is InventoryRepository, isFalse)——这条是错的： 同一个 InventoryDatabase 对象本来就同时实现了仓储与待办写口， 那是实现类的事实，跟接口的边界无关。已改成上面三条正确口径。 教训：要证明的是「接口的边界」，不是「对象的类型」。
