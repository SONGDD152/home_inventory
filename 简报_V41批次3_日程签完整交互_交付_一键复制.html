四、裁定④（只往后推不许回拉）—— 单独摊开讲

判据：基准 = next_due_at ?? 源条目原到期日 ?? 现在

// lib/data/inventory_database.dart · InventoryDatabase.defer
final anchor = (existing?[columnNextDueAt] as num?)?.toInt() ??
    await _sourceDueAt(db, sourceType, sourceId) ??
    now;
if (dueOn.millisecondsSinceEpoch < anchor) {
  throw ArgumentError.value(
    dueOn, 'dueOn', '延期只能往后推，不能早于当前提示日期');
}
场景结果怎么验的
选了早于当前提示日被拒，抛 ArgumentError；状态行一个字不动（连 defer_count 都不加——这次延期压根没发生）专项断言「抛错」+「readState 仍为 null」
选了等于当前提示日允许（不构成「早于」）→ 次数 +1专项断言 deferCount == 2
选了往后正常写入 next_due_at，次数 +1，原因落 handle_note专项断言
已延到 10 天后，再延到 3 天后被拒——基准是 next_due_at，不是原到期日专项断言「抛错」
为什么校验必须放数据层：UI 只是入口，数据层才是唯一能保证这条规矩成立的地方。只在 UI 拦的话，任何绕过 UI 的调用（语音、备份恢复、将来的批量操作）都能把提示时间往回拉。
UI 侧也做了：日期选择器 firstDate 直接设在「当前下一次提示日」→ 用户挑不到更早的日子（不是挑完再被驳回）；「延到明天」在会构成回拉时禁用并写明「早于当前提示日」。

六、自曝：本批做的两个判断 + 三条待裁示

自曝 1 · 修了两处源码级锁的口径缺陷（v43 / v44）。
原实现直接 readAsStringSync() 全文匹配 —— 注释里提到类型名就误报。 实际后果：本批我在注释里写「数据层还会再校验一次（见 InventoryDatabase.defer）」，锁就红了。
问题不在我的注释，在锁测错了东西：它测的是「文档用词」，不是「能力边界」—— 逼着写注释的人绕着某个词说话，真正的边界反而没人管。
改法：与 v41 同款 codeOnly()（剥注释行后再查）+ 补反向锁。改的是测法，不是放宽标准——锁的禁止清单一个字没减，还多了一条。
自曝 2 · 裁定③的实现方式变了（口径不变）。
批次 2 里「日程签不碰提醒交互」靠给 _TodoEntryRow 传 showActions: false 实现。 批次 3 日程签拆成独立组件后，这个参数恒为 true（已无第二个调用点）→ 删掉它， 改为从设计上就没有延期/备注按钮。
裁定③说「勾选保留，只去延期/备注」——勾选保留（写 todo_states），延期/备注整个组件里都不存在。口径比原来更硬。

三条待元宝裁示 / 追认

#事项buddy 的处理与理由
1 系统类提前量用「显式覆盖」而非改推导表 见第二节。理由：改推导表会连带把日程类高优先级从 3 天改成 2 天（越权改裁定②）。请确认「优先级与提前量解耦」这个处理方式可接受，或直接裁「日程类高优先级也统一改成 2 天」（那我会去改推导表）。
2 重复规则只存不展开 设了「每周」到期后不会自动滚出下一条。要展开得先定语义：（甲）完成后自动新建一条下一实例（保留历史）（乙）改 due_at 滚到下一期（不留历史）。（甲）更符合「已完成要留着，日报看得到今天做完了什么」这条既有口径，但会让 reminders 行数增长。请裁一个，我下一批做。
3 概览区用回调而非写口 见第五节。这是让元宝批过的「概览页不持仓储类型」一个字都不用改的方案。代价：概览区不能直接发起写操作，必须经组合根回调——多一层间接。请确认这个方案；若元宝更希望概览区直接持窄写口（ReminderEditor），我改，但那条锁要相应放宽到「只禁账类写口」。
