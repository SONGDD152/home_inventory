〇、先报一处对回执的自我升级（元宝看这里）

回执第四节我写的是「reminders 表加 defer_count + handle_note 两列，schema v11→v12」。重新推演后这个方案有洞，本件改掉它。

洞在哪为什么致命
借出到期条目不属于 reminders 表 元宝 E5 要求借出到期条目也能打勾。若状态存在 reminders 表，就只能把借出到期「投影」成 reminders 行来存状态 —— 投影行与 loans 的真实状态会漂移（还了钱但投影行还在、投影行删了但借出还在）。

改成什么：新增第 9 张表 todo_states，作为所有催办条目状态的唯一权威源（日程类 + 系统类共用）。reminders 表一列不动。

三个连带好处：
  1. 迁移从「ALTER TABLE ADD COLUMN ×2」降为「CREATE TABLE IF NOT EXISTS」→ 幂等天然满足，连 _addColumnIfMissing 都不需要；
  2. 不碰任何旧表旧列 → 旧备份兼容零风险，V4.0 的备份文件在 V4.1 里原样可恢复；
  3. reminders 原有 status/done_at 字段保留不动（不删不改）→ 老代码与老备份读路径不变，回滚安全。

一、架构决策 1：概览的写边界怎么拆（PM 已拍板，元宝请复核）

落地成两个互不相通的接口，概览页同时持有它们，但能力面完全隔离：

接口文件能读能写实现者
OverviewReader（已存在，一字不改） lib/domain/overview_reader.dart 物品/在库/在借/废弃/总拥有/守恒账平 无任何写方法 InventoryOverviewReader
TodoStateWriter（新建） lib/domain/todo_state_writer.dart 待办条目状态 只写 todo_states 表 InventoryDatabase（新增 implements）
类型层面的保证（不是靠自觉，是靠签名）：TodoStateWriter 的方法入参只有字符串 entryId + 枚举值，拿不到任何仓储句柄、拿不到 items/loans/locations 任何一个。所以「概览不能改账」这条元宝 I③ 已放行的地基，在 V4.1 之后依然在编译期成立——概览就算想改账，也没有那条路。

接口草案（施工时按此实现）

// lib/domain/todo_state_writer.dart（新建）
/// V4.1：待办条目状态写入口。
///
/// 与 [OverviewReader] 严格分离——概览页持有两个接口：
///   - OverviewReader：只读账目（物品/在库/在借/守恒），无任何写方法
///   - TodoStateWriter：只写 todo_states 表，不触碰任何账目字段
///
/// 类型层面的保证：方法入参只有 entryId 字符串，概览拿不到仓储句柄，
/// 因此「概览改不了账」在编译期成立。
abstract interface class TodoStateWriter {
  /// 读单个条目的待办状态（null = 从未处理过）。
  Future<TodoState?> readState(String entryId);

  /// 读全部待办状态（概览页按 entryId 匹配条目）。
  Future<List<TodoState>> loadStates();

  /// 标记已处理 / 撤销已处理（划线灰化的开关）。
  Future<void> markDone(String entryId, {bool done = true});

  /// 延期：延期次数 +1，写入原因，更新下一次提示时间。
  Future<void> defer(String entryId, {String? reason, int days = 1});

  /// 写处理备注 / 延期原因（导出时一并带出）。
  Future<void> setNote(String entryId, String note);

  /// 自动延期同步：把「已过期且未处理」的条目推进一天，延期次数 +1。
  /// 幂等：同一天重复调用不会重复加次（next_due_at 已推到明天）。
  Future<int> syncOverdue(DateTime now);
}

todo_states 表（v12 第 9 张表，两库齐平）

CREATE TABLE IF NOT EXISTS todo_states (
  entry_id     TEXT PRIMARY KEY,          -- 'reminder_<id>' | 'loan_<id>'
  state        TEXT NOT NULL DEFAULT 'pending',  -- pending | done | deferred
  done_at      INTEGER,                   -- 处理时间（UTC 毫秒）
  note         TEXT,                      -- 处理备注 / 延期原因
  defer_count  INTEGER NOT NULL DEFAULT 0,-- 延期次数，按「次」累计，永不按天重置
  next_due_at  INTEGER,                   -- 延期后的下一次提示时间
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_todo_states_state     ON todo_states(state);
CREATE INDEX IF NOT EXISTS idx_todo_states_next_due ON todo_states(next_due_at);
「自动延期」为什么要落在 next_due_at 而不是推 reminders.due_at？
推 reminders.due_at = 概览（或日报页）去写日程表 → 「概览只写待办状态」的边界就漏了。改成在 todo_states 记 next_due_at，日程表零改动，边界不漏。

「每天最多自动延期一次」的口径：next_due_at = max(effectiveDue + 1 天, 明天)。 若一条提醒已过期 5 天，当天只 +1 次（不是 +5 次），否则计数会一天涨 5 次，用户看到的「已延期 N 次」失真。

「同一天多次延期算多次」：手动延期（用户点延期按钮）每次 +1，一天点 3 次就是 3 次 ✓； 自动延期每天最多 +1 次 ✓。两者共用同一个 defer_count，跨天只增不减。

二、架构决策 2：E1 真 bug 怎么修（生活区借出到期被工作区覆盖吞掉）

根因是两个源共用同一个 id 和同一个 displayName，而概览页拿 displayName 当 Map 的 key：

// 现状 lib/ui/overview_page.dart:58-61
final entries = <String, List<OverviewEntry>>{};
for (final source in widget.sources) {
  entries[source.displayName] = await source.loadEntries();  // ← key 用错了
}

修法两道，缺一不可（只改名是糊弄）：

道改什么落点
① Map 的 key 从 displayName 换成 source.id（唯一标识做 key，展示名只管展示） lib/ui/overview_page.dart:60、:115、:150-151
② 源的 id 与 displayName 带域：id = 'loan_due_${domain.id}'；displayName = '${domain.label}·仓储借出到期'（元宝 E2 要求的「生活区·仓储借出到期」格式） lib/domain/reminder_sources.dart:16,19（借出）、:47,50（日程）

为什么 id 要带域、不能只在 displayName 上带

id 是去重与配对的唯一依据。V4.1 里条目要跟 todo_states 配对（entryId ↔ 待办状态），如果 id 不带域，生活区和工作区的 loan_1 会撞成同一条，勾一边两边都变。带域后 entryId 形态是 loan_1@work / loan_1@life，天然隔离。

构造签名变更（强制传域，编译器兜底）

// 改后
class LoanDueReminderSource implements ReminderSource {
  const LoanDueReminderSource(this.repository, this.domain);  // ← 域必填
  final InventoryDomain domain;
  @override String get id => 'loan_due_${domain.id}';
  @override String get displayName => '${domain.label}·仓储借出到期';
}
调用点只有 4 处，全改成本很低：lib/ui/home_page.dart:2299、:2300、:2305、test/v40_multidomain_test.dart:324（后者是我自己写的 V4.0 专项，不属 461 条旧红线）。
域必填而非可选带默认值，是为了让编译器强制每个调用点都显式声明域 —— 否则默认 life 会让工作区的源悄悄用 life 的 id，又是同一个坑。

五、架构决策 5：工作域提醒（PM 已拍板「不新建」）
